## 2. 铁律

### 2.1 上下文 100k 规则

用户原话：每个对话（包括老板会话），单次请求上下文超过 100k，后三轮内必须停下。

**执行口径**（若理解有偏差，以用户纠正为准）：

1. 一旦上下文超过 100k，之后**最多再进行 3 轮**对话。
2. 第 3 轮之内必须完成交接文件（按 `handoff/TEMPLATE.md`），然后告知用户「可以关闭」。
3. 停止后不得再开新的实现或新的子任务。
4. 预防：
   - 单个工作会话只做一个任务编号（如 A-1 或 B-2），不跨任务。
   - 禁止整文件读取超过 800 行的文件，用 `offset`/`limit` 或 `grep`。
   - 老板会话只读交接文件和关键章节，不通读代码。

### 2.2 规划与执行分离

- 规划类请求：只写 `docs/planning/`，不改源码（见 memory `feedback-planning-docs-folder`）。
- 执行类：只有用户说「开工」或「执行」后才改源码。
- **授权范围**：工作会话开启提示词里列出的任务编号即为授权范围。完成后不自动延伸到下一个任务编号。

### 2.3 TDD

- 新增后端代码、纯函数：先写测试（RED），确认失败，再实现（GREEN），再重构（IMPROVE）。
- 覆盖率口径以 03 的 D-3 为准：`task_service.py`、`rag/service.py`、`api/stats.py` 目标 ≥ 80%。未达标如实写。

### 2.4 Git 规则

| 项 | 规则 |
|---|---|
| commit | 只有开启提示词中写明「允许在分支 X 上 commit」才可以 commit。**不 push，不 merge 到 master。** |
| commit 格式 | `<type>: <描述>`，type 取 feat / fix / refactor / docs / test / chore / perf / ci |
| commit 结尾 | 必须加一行：`Co-Authored-By: Claude Haiku 5.5 <noreply@anthropic.com>` |
| PR 描述结尾 | `🤖 Generated with [Claude Code](https://claude.com/claude-code)` |
| 提交前 | 运行 verify（verification-loop） |
| 基线提交（P0-1） | 提交前必须 `git diff --cached` 检查。**当前已暂存 34 个 `.playwright-cli/` 删除**，需用户决定是否一并纳入，不得默默带入 |
| 不提交 | `backend/.env`、任何 key、`handoff/LOCK.md`、`node_modules`、`.venv` |

### 2.5 分支与 worktree

**分支结构**

```
master
└─ feat/ui-upgrade-2026-10        ← P0-1 基线之后切出，所有改动在此集成
   ├─ feat/ui-a                   ← SA（方案 A）
   ├─ feat/ui-b                   ← SB（方案 B）
   └─ feat/ui-c                   ← SC（方案 C）
```

**创建 worktree**（在主仓库执行，路径与主仓库同级）：

```bash
cd /d/My_Grand_Projects2026/14Day-Software-Fighter
git worktree add ../wt-a -b feat/ui-a feat/ui-upgrade-2026-10
```

**worktree 不含 gitignored 文件**，工作会话开工前必须自行准备：

| 缺失项 | 处理 |
|---|---|
| `backend/.env`（含 LLM 配置） | 从主仓库复制过去。**不得提交，不得打印内容** |
| `backend/.venv` | 直接用主仓库的解释器：`D:\My_Grand_Projects2026\14Day-Software-Fighter\backend\.venv\Scripts\python.exe`，或在 worktree 内新建 venv |
| `frontend-web/node_modules`、`patient-app/node_modules` | 在 worktree 内 `npm ci` |
| `docs/planning/`（未跟踪） | 不在 worktree 中。**读写都用主仓库绝对路径** |

### 2.8 依赖门与并行

```
P0-1 基线（需用户确认）
 └─ P0-2 → P0-3（需锁，重置演示库）→ D-1 pytest      ← S0 串行
      │
      ├─ G0 门：S0 交接文件状态为「完成」
      │    ├─ SA  A-1 → A-2 → A-3 → A-4                 ← 并行
      │    ├─ SB  B-1 → B-2 → B-3                       ← 并行（B-1 素材不占锁，P0-1 后即可开始）
      │    └─ SC  C-1 → C-2 → C-3 → C-4                 ← 并行（C-1 不依赖 pytest）
      │
      ├─ G1 门：SA、SB、SC 分支完成，用户已合回 feat/ui-upgrade-2026-10
      │    └─ SD  D-2 → D-3 → D-4 → D-5                 ← 串行
      │
      └─ G2 门：SD 完成，全部代码冻结
           └─ SE  E-1 → E-2 → E-3 → E-4 → E-5 → E-6     ← 串行
```

**关键依赖**：
- A-1 与 C-2 的测试需要 pytest，因此必须等 G0。
- SD 要在 SA、SC 的后端改动合并后再迁移，否则 `test_ai_fallback`（T14）等会对着旧代码写。
- C-5（说明书外发条款）属于 SE，且**必须等用户确认外发条款**（03 §10 第 3 项）。

**并行上限**：同时运行的工作会话 **≤ 3**。

### 2.9 完成定义（DoD）

对应 03 §9，每个任务完成前必须同时满足：

1. 对应测试通过，且先写的测试确实经历过 RED → GREEN。
2. `run_acceptance` 相关步骤不回退（以 P0-3 的基线数字为准）。
3. 文档同步登记到交接文件（实际同步由 SE 在 E-4 完成）。
4. 截图或证据存入 `docs/evidence/ui-upgrade-2026-10-<任务编号>/`。
5. 不引入真实身份信息、真实 key，未审核内容标注 DEMO-未审核。
6. 交接文件已写，锁已释放。

### 2.10 交接

- 每个工作会话结束时（或触发 100k 时），在 `D:\My_Grand_Projects2026\14Day-Software-Fighter\docs\planning\handoff\` 下写交接文件，文件名：`<任务编号>-<日期>.md`，例如 `S0-2026-10-19.md`。
- 格式以 `handoff/TEMPLATE.md` 为准。
- 交接文件的「状态」字段必须是 `完成`、`进行中`、`阻塞` 或 `100k中断` 之一。依赖门的判断只看这个字段。
- 向用户汇报只说三件事：交接文件路径、结果（附原始数字）、阻塞或需决定的问题。

### 2.11 证据诚实

- 没跑的测试写「未跑」，不写「通过」。
- 没有真机、没有 key 时，对应验收项标注「缺失」，不宣称完成。
- 数字不美化，失败原样记录。

### 2.12 安全与合规

- key 只写 `backend/.env`。不粘贴进对话、文档或仓库，不打印。若已粘贴，提醒用户去供应商后台轮换。
- 问答外发内容只允许「问题文本 + 已审核片段」。不含 `patient_id`、姓名、手机号、身份证、计划信息。
- 指导图示、素材一律标注「DEMO-未审核」，不宣称为厂家官方图。
